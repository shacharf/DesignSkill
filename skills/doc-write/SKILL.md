name: doc-write
description: Write or revise human-readable system-design pages with a main ideas document, recursively understandable modules, and technical detail only at the deepest useful level.
---

Read [the reading contract](references/reading-contract.md) before drafting or restructuring. Read the relevant module, parent overview, neighboring interfaces, supporting sources, and decisions. Use actual passages; do not invent missing design facts. The user's writing request authorizes relevant design edits; no manuscript-specific approval step applies.

Explain purpose and core mechanism before internal parts. Introduce vocabulary when it becomes necessary. Establish the main story in `design.md`, then develop the selected module recursively. Choose bullets, short prose, tables, or figures according to what explains the idea best; none is universally preferred. Add a labeled figure or example when it helps, with a brief explanation of its takeaway. Roughly three to five peer concepts is a cognitive target, not a reason to omit constraints. Keep unresolved choices visible where they matter.

Keep each page understandable when opened directly: state its purpose, essential context, responsibilities, and interactions. Link to deeper mechanisms and specifications instead of embedding all detail. Small leaves need no artificial children or boilerplate sections. Preserve precise edge cases, interfaces, algorithms, and configuration in leaf pages or linked detail, rather than deleting them to shorten the design.

When an edit to `design.md` or a module adds a requirement or changes a decision's status, update the matching line in the Key decisions at a glance section of `design.md` in the same edit; create the section if it is missing. Keep each line short and linked, and do not tag a proposal as Decided.

Edit coherently rather than accumulating summaries. Respect manual edits and existing authorization. After a change, inspect parent summaries and affected neighboring modules; update stale explanations within the requested scope and record remaining work. Keep alternative history and detailed rationale in linked discussions. Source notes retain provenance; link design claims to supporting notes where useful without cluttering the narrative. After substantial drafting or revision, apply doc-review to the changed pages and affected connections before calling the draft reviewed. Check ambiguity and missing behavior as well as readability; fix clear issues within scope and record unresolved design questions without inventing answers. Recheck the affected findings after corrections, rather than recursively reviewing the entire design. Small wording edits need no full pass. Run `docagent checkpoint` after saving. Report the changed explanation and any material unresolved choice.

## Delegating editorial work
Delegate substantial wording, heading, caption, or formatting work on a well-understood page when the intended meaning is already established. On Codex, explicitly select `gpt-6-luna` at `low` effort; respect user settings and the project's delegation policy. If a suitable lower-cost worker is unavailable, work in the main thread. Give the worker fresh context containing the assigned page, the reading contract, relevant parent/interface context, accepted decisions, and the precise editorial objective.

Prefer proposed text returned to the main agent. If direct edits are useful, assign exclusive ownership of named files; use at most two workers on independent pages, and do not concurrently edit their files. Workers must preserve meaning, flag uncertain interpretations, and return proposed changes with source locations and checks performed. They do not restructure the hierarchy, decide unresolved design questions, edit shared records, checkpoint, or delegate further. The main agent verifies preserved meaning and consistency with neighboring pages, integrates the result, and performs the scoped review and checkpoint. Tiny edits and architecture changes stay in the main thread.
