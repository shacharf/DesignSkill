name: doc-design
description: Organize rough system documents into a hierarchical design; guide module-focused work, maintain TODOs, and save or resume design discussions in a docagent project.
---

Run `docagent status --json` once to recover the saved working brief, selected module, and discussion resume. Read named excerpts deliberately. Start with the user's goal and sources; help shape `design.md` before elaborating individual modules. Apply [the reading contract](references/reading-contract.md) to every document you author, including TODOs and working summaries, as well as when shaping the hierarchy.

## Focus and navigation
Use `docagent tree` to understand the hierarchy and `module show ID` for a known module. When moving from requirements to component design, start from the component groups in the Key decisions at a glance section of `design.md`: propose them as top-level modules, carry each group's Req/Decided items into its module as starting constraints, and turn its Open items into that module's TODOs. Create modules with `module create "Title" --parent ID`; select with `module select ID`. Keep one immediate design question in focus. Save conversation-only reasoning before switching. Direct selection changes pointers only and cannot summarize chat. Starting a new project does not require an invented discussion if there is nothing yet to preserve.

Use doc-sources for extracting inputs, doc-brainstorm for alternatives, doc-write for design prose, doc-review for readability and consistency, and doc-help for guidance. After substantial drafting or revision, apply doc-review to the changed pages and affected connections; review overall consistency at major milestones. Do not force all skills through every small task. Ask only questions whose answers materially affect the design; continue independent work where possible.

## Delegating bounded work
For substantial independent extraction, wording, or module review, delegate using the project AGENTS.md delegation policy and the relevant doc-sources, doc-write, or doc-review instructions. Start with one worker; use a second only for independent work. Keep architecture, reconciliation of conflicting sources, hierarchy decisions, shared TODOs, active pointers, and final integration in the main thread. Pass each worker the applicable writing rules and task-specific context; workers do not perform the save/switch protocol or spawn further agents. Await and inspect results before reporting completion, then save accepted work through the normal checkpoint workflow. Small tasks and deterministic commands need no delegation.

## Work tracking and progressive planning

`TODO.md` is the authoritative, Docsify-readable agenda. Top-level topics have purposes and known dependencies; their subtopics do not exist until the topic is current. There is no task-count limit. Use doc-brainstorm's agenda mode for planning and its discussion mode for focused work. Start the current topic with `docagent todo --start ID`, then add its subtopics with `docagent todo "Question" --parent ID --why "Motivation"`. Briefs are prepared in the linked discussions before handoff.

`docagent todo --next` identifies the current topic's next subtopic or requests planning/closure. It does not start another parent. `todo --show ID` provides the full saved discussion brief, parent reference, and cumulative planning summary; read these when resuming, not just the bounded resume. The user can start a fresh main chat with a suitable lower-cost model. Recommend a different model/effort only when useful; the host/user controls switching.

Mark done only after a meaningful discussion outcome is saved. Completing a parent also requires updating WORK.md's cumulative summary with its outcome link, and updating the Key decisions at a glance section in `design.md` for every requirement or decision whose status the topic added or changed. Revisit old and new open questions: add/update actionable TODOs and use `--follow-up-for ID` for lineage, or `todo --link EXISTING_ID --follow-up-for ID` to reuse an open successor. Defer only after an open follow-up is linked (`--defer ID --reason TEXT`); retire obsolete tasks with `--drop ID --reason TEXT`. Preserve motivations, useful history, user priorities, and IDs. Changes in understanding can require replanning immediately, without waiting for completion. Save before switching or ending; direct commands cannot summarize chat.

## Save and resume
At meaningful conclusions and before switching or ending, save accepted, rejected, deferred, and uncertain ideas with reasons in the current `discussions/` record. Create one using `discussion create "Question" --module ID` and select it if needed. Keep working history out of the reader-facing design. Preserve examples, constraints, source locations, and changed understanding; do not append repetitive transcripts.

Update the managed resume block: Question, Current understanding, Immediate focus, Next step, Supporting material. Maximum 5000 characters. Maintain the managed working brief in `WORK.md` as the cumulative planning summary: current direction, important decisions and reasons, constraints, uncertainties, and implications for the next topic, linked to detailed outcomes; maximum 3000 characters. Update it before closing each parent and when shared understanding changes. These operational bounds do not constrain leaf specifications. Keep the active module/discussion pointers consistent. Run `docagent checkpoint`; correct relevant failures, then report the saved focus and next step. Mention pending or failed indexing without treating it as lost Markdown. Do not report an unsaved conversation as checkpointed.

Markdown is authoritative. Search unknown locations with `docagent search "phrase"`, optionally `--hybrid`; read exact passages before relying on them. Search may lag edits, and a miss is not proof of absence. Use `index status` and explicit `index flush` for recovery. Do not use answer-generation search, unrelated collections, or automatic Git operations.
